# Correctness check: grid join vs. lateral join vs. HadathSQL UDF

**Date:** 2026-10-02
**Question:** Do the PostGIS lateral join and the PostGIS generate-grid-then-join assign points to the same squares, and are the assignments correct?

## Answer

Yes. On three datasets, the lateral join (with its `ST_Intersects` predicate) and the grid join assigned every point to the same square, and that square is the expected one. The HadathSQL UDF is also correct; it uses a grid with a different origin, so its cell identifiers and cell counts are not comparable with PostGIS's.

The lateral join is correct only with the `ST_Intersects` predicate. Without it, a small share of points is assigned to more than one square. With it, the lateral join is also correct for points that lie exactly on a cell edge or corner: each such point is assigned to exactly one square, the expected one.

## Methods checked

| Name | Query pattern |
|---|---|
| Grid join | `FROM docs d JOIN ST_SquareGrid(L, <extent of docs>) g ON ST_Intersects(d.geom, g.geom)` |
| Lateral join | `FROM docs d CROSS JOIN LATERAL ST_SquareGrid(L, d.geom) g WHERE ST_Intersects(d.geom, g.geom)` |
| Unfiltered lateral join | the lateral join without the `WHERE` clause |
| UDF | `hsql_spatial_partition(x, y, L)` |

## How the check works

The check does not compare totals. For each dataset it stores, for every point, the square (or cell) that each method assigns to it, and then compares the stored assignments:

1. **Grid join vs. lateral join:** the sets of `(point id, i, j)` rows must be identical.
2. **Each PostGIS method vs. the expected square:** the expected square is computed from the coordinates alone as `i = floor(x / L)`, `j = floor(y / L)`. This is how `ST_SquareGrid` numbers its squares, whose grid starts at the coordinate origin (0, 0).
3. **One square per point:** every point id must appear exactly once per method.
4. **Per-cell counts:** the `(i, j, number of points)` rows of the two PostGIS methods must be identical.
5. **UDF:** every point must lie inside the half-open cell the UDF returned for it. The UDF's grid starts at the south-west corner of the Web Mercator plane, (-20037508.34, -20037508.34), so its cells are checked against that origin, not against the PostGIS squares.

## Datasets

The datasets are generated by `eval_vs_postgis.py` with the same seeds as the runtime benchmark, so they are the same points that were timed.

| Dataset | Points | Cell side | Description |
|---|---|---|---|
| Compact | 1,000,000 | 1 km | One Gaussian cluster (standard deviation 8 km) around Riyadh |
| Country | 100,000 | 1 km | 95% in clusters around five Saudi cities, 5% uniform over a 2,350 km by 1,950 km box |
| World | 100,000 | 10 km | 95% in clusters around twelve world cities, 5% uniform between latitudes -55 and 70 |

Sizes were kept at or below one million points so that the grid join, the slowest method, finishes in a few minutes.

### What the results mean

- **The grid join and the lateral join are equivalent on these datasets.** They agree on every point and on every cell count, and both match the expected square.
- **The `ST_Intersects` predicate is required in the lateral join.** Without it, `ST_SquareGrid` also returns a neighboring square for points very close to the upper edge of their square, so 0.01% to 0.08% of the points here are assigned to more than one square. In the compact dataset, 762 points produce 764 extra assignments, so two of them were assigned to three squares.
- **The UDF is correct on its own grid.** Each point lies inside the cell returned for it, and each point gets exactly one cell.
- **The UDF's cell counts differ from PostGIS's because the grids differ, not because either is wrong.** The two grids have the same cell size but different origins, so they cut the same points into slightly different groups (for example 3,383 against 3,368 non-empty cells).

## Points exactly on a cell boundary

Random points do not fall exactly on a boundary, so that case was tested with four hand-placed points on a 1 km grid. The table gives the number of squares each method assigns to the point.

| Test point | Grid join | Lateral join | Unfiltered lateral join |
|---|---|---|---|
| Inside a square | 1 | 1 | 1 |
| 0.0001 m below the upper edge of its square | 1 | 1 | 2 |
| Exactly on an edge shared by two squares | 2 | 1 | 1 |
| Exactly on a corner shared by four squares | 4 | 1 | 1 |

- **The grid join assigns a point exactly on a boundary to every square that touches it.** Its join condition, `ST_Intersects`, is true on the boundary of a square. `ST_Intersects` is the cause here, so it cannot be the fix; a half-open comparison of the coordinates with the square's bounds would be needed.
- **The lateral join assigns such a point to one square.**
- **This is the one case in which the two PostGIS methods differ.** It did not occur in any of the generated datasets.
- The UDF uses half-open cells, so it assigns a boundary point to exactly one cell.

### Lateral join on many exact-boundary points

Four hand-placed points are thin evidence, so the lateral join was also run on 600,000 points placed exactly on boundaries of the 1 km grid, at random positions across the whole Web Mercator plane (x between -20,000 km and 20,000 km, y between -7,000 km and 11,000 km).

| Points | Count | Not assigned to exactly one square | Assigned to a square other than the expected one |
|---|---|---|---|
| Exactly on a corner (x and y are multiples of 1,000) | 200,000 | 0 | 0 |
| Exactly on a vertical edge (x is a multiple of 1,000) | 200,000 | 0 | 0 |
| Exactly on a horizontal edge (y is a multiple of 1,000) | 200,000 | 0 | 0 |

Three hand-placed corners with other cell sizes (1,500 m, 250 m, and 10 km at negative coordinates) also got exactly one square, the expected one.

Why the lateral join is correct in both situations:

- **Point exactly on an edge or corner:** `ST_SquareGrid` called on that point returns a single square, the one above or to the right of the boundary. This matches the `floor` rule, so the square is the expected one. The `ST_Intersects` predicate has nothing to remove.
- **Point just below an edge:** `ST_SquareGrid` returns the point's square and the neighboring one. The point does not touch the neighbor, so the `ST_Intersects` predicate removes it.

`ST_Intersects` on its own is not an "inside" test, since it is also true on a square's boundary. The lateral join is correct because of the two steps together.

## Limits of this check

- The data is synthetic, and no point of the three generated datasets lies exactly on a boundary; boundary behavior was tested separately, as described above.
- The exact-boundary test uses whole-meter cell sizes. A fractional cell size could place edges at coordinates that are not exactly representable, and that was not tested.
- That `ST_SquareGrid` returns a single square for a point exactly on an edge was established by experiment on PostGIS 3.6.4, not from its documentation.
- The largest dataset checked point by point has one million points. In the runtime benchmark, the grid join and the lateral join also reported the same number of non-empty cells and the same number of points on all 15 tables on which both ran, up to ten million points, but that is a comparison of totals only.
- Shifted grids were not checked.

## Environment

- PostgreSQL 18.6 (Homebrew), PostGIS 3.6.4 (GEOS 3.15.0, PROJ 9.9.0), macOS 15.7 on Intel.
- UDF version: branch `parallel-safe-partition-udfs` (commit `95a4073` plus the uncommitted `IMMUTABLE PARALLEL SAFE` changes). These changes do not affect the values the UDF returns.

## How to reproduce

From the repository root, with `psql` on the path and PostGIS installed:

```
python3 spatial_partition/evaluation/check_equivalence.py
```

The script creates a scratch database `hsql_equiv_check`, runs the checks, prints one block per dataset and one per boundary test, and drops the database. To run only the boundary tests, which take a few seconds, add `--boundaries-only`. The raw output of the run described here is in `correctness_check_output.txt`.
